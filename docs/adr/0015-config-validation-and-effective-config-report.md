# ADR 0015: Validate configuration at startup and report it safely

## Status
Accepted — implemented and verified in this environment (`mvn verify`
green, 109 tests; both the validation and the report proven against the
real packaged jar, not just unit tests).

## Date
Proposed 2026-08-13, Accepted 2026-08-13.

## Context
Master brief §10–11 calls for configuration that's externalized (already
true — `application.yml` plus environment variables) and *validated*, plus
visibility into what the server actually resolved at startup. Today,
`QueryLimitsProperties.maxRows() <= 0` would only surface as a confusing
`IndexOutOfBoundsException` deep inside `Db2QueryAdapter.executeQuery`'s
`rows.subList(0, maxRows)` call, on the first real query - not at boot,
and not with a message pointing at the misconfigured property. Nothing
today tells an operator what capability profile, schema allowlist, or
resource limits the server actually resolved without reading environment
variables by hand.

## Decision drivers
- Invalid configuration should fail fast at startup with a clear message,
  not surface later as an unrelated-looking runtime exception.
- An effective-config report must never log a credential — this project's
  established defense-in-depth habit (ADR 0002's three independent
  read-only layers; ADR 0010/0011/0012's shared safe-attribute
  vocabulary) applied to configuration reporting specifically.
- A diagnostic feature must not become a new way for the application to
  fail to start — logging what's wrong is not the same as crashing over
  it.

## Considered options
1. **`spring-boot-starter-validation` (Bean Validation / Hibernate
   Validator) on the existing `@ConfigurationProperties` records, plus a
   small `@EventListener(ApplicationReadyEvent.class)` component logging
   the safe subset of resolved configuration.** Standard Spring Boot
   mechanism — annotate record components with `jakarta.validation`
   constraints, mark the record `@Validated`, and an invalid value fails
   `SpringApplication.run()` with a message naming the exact property,
   its value, and origin (environment variable vs. YAML vs. default).
2. **Hand-written validation in each properties record's compact
   constructor** (e.g. `if (maxRows <= 0) throw new
   IllegalArgumentException(...)`). Rejected: works, but reinvents what
   Bean Validation already does well, and loses the structured
   property/value/origin reporting Spring Boot's binder gives for free
   when using real constraint annotations.
3. **No startup validation; document the constraints and trust
   operators.** Rejected: contradicts the master brief's explicit call
   for validated configuration, and this project's whole posture is
   defense-in-depth rather than trusting configuration to be correct.

## Decision
Add `spring-boot-starter-validation` (pulls in `hibernate-validator` and
`jakarta.validation-api` only - no servlet container, confirmed via
`mvn dependency:tree`). Annotate `QueryLimitsProperties.maxRows`/
`timeoutSeconds` with `@Positive`, `QueryPolicyProperties.allowedSchemas`'s
elements with `@NotBlank`, and `CapabilityProperties.capabilityProfile`
with `@NotNull`; mark all three `@Validated`. Add
`EffectiveConfigReporter`, an `@EventListener(ApplicationReadyEvent.class)`
component that logs capability profile, allowed schemas, resource
limits, and a credential-redacted datasource URL plus Hikari pool
settings — to stderr like every other log line (ADR 0001), never stdout.

## Consequences
- **Validation proven to actually fire against the real packaged jar**,
  not just a unit test: starting it with `DB2MCP_QUERY_MAXROWS=0` fails
  with `Property: db2mcp.query.maxRows / Value: "0" / Origin: System
  Environment Property "DB2MCP_QUERY_MAXROWS" / Reason: must be greater
  than 0`; a blank entry in `allowedSchemas` fails with `Property:
  db2mcp.allowedSchemas[1] / Reason: must not be blank`. Both are exactly
  the property, value, and reason an operator needs, generated by the
  framework rather than hand-written.
- **A real bug in `EffectiveConfigReporter` itself, found by smoke-testing
  it rather than assumed correct:** the first version called
  `Environment.getProperty("spring.datasource.url")` directly, which
  throws `PlaceholderResolutionException` when `DB2_HOST`/`DB2_PORT`/
  `DB2_DATABASE` aren't set. That's an expected, ordinary state (secrets
  not wired up yet, or exactly the state every earlier packaged-jar smoke
  test in this project's history has actually been running in — see
  below) - and critically, `SpringApplication.run()` itself does **not**
  fail in that state; the DataSource bean is created successfully and the
  application starts, since Hikari doesn't validate the JDBC URL string
  until a connection is actually requested. A diagnostic listener
  crashing `ApplicationReadyEvent` handling in a state the application
  otherwise tolerates fine defeats its own purpose. Fixed by catching the
  resolution failure and reporting `"(unresolvable - one or more
  placeholders not set)"` as the value instead of propagating the
  exception - confirmed by rerunning the exact failing scenario against
  the real jar (`Registered tools: 8`, effective-config line printed with
  the unresolvable marker, no `Application run failed`, process stays
  up).
- **A related methodology finding, worth stating plainly:** every
  previous packaged-jar smoke test in this project's history (ADR 0005,
  0011, 0012, 0013, 0014's verification sections) set an environment
  variable named `DB2MCP_DB_URL` intending to point the server at an H2
  in-memory database. That variable does not exist —
  `spring.datasource.url` is templated as
  `jdbc:db2://${DB2_HOST}:${DB2_PORT}/${DB2_DATABASE}` in
  `application.yml`, so the real variables are `DB2_HOST`, `DB2_PORT`,
  `DB2_DATABASE`, `DB2_USER`, `DB2_PASSWORD` (or a direct
  `SPRING_DATASOURCE_URL` override to replace the whole templated value,
  e.g. with an H2 URL). Those earlier smoke tests were still checking
  real things - registered tool count and zero network exposure, neither
  of which depends on the datasource actually being reachable - so
  nothing they concluded was wrong. But the datasource itself was never
  H2 in any of them, just an unresolved placeholder string Hikari never
  got around to validating during a short-lived startup-and-shutdown
  smoke test. Recorded here rather than silently corrected, since it's
  exactly the kind of unverified assumption this project's discipline
  exists to catch - just caught one layer later than ideal.
- **Verified end-to-end with real (fake) credentials**: starting the
  packaged jar with `DB2_USER=scott DB2_PASSWORD=tiger` and other DB2_*
  variables set, the effective-config line correctly resolves and prints
  `datasourceUrl=jdbc:db2://dummyhost:50000/ITSMDB` while `grep -c
  "scott\|tiger"` across the *entire* stderr log returns `0` — the
  credentials genuinely never appear anywhere, not just absent from the
  one log line under test.
- **Full suite: 109 tests** (up from 108), all green under `mvn verify
  -DskipITs`; the JaCoCo policy-package gate (ADR 0014) is unaffected
  since `EffectiveConfigReporter` lives in `configuration`, not `policy`.
  Packaged-jar smoke test re-run across three scenarios (no DB2_* vars,
  invalid `maxRows`, valid full configuration): correct behavior in all
  three, stdout stays 0 bytes, zero `lsof` network file descriptors.

## Verification / enforcement
`SpringApplication.run()` fails fast on an invalid `db2mcp.*` property
value via `spring-boot-starter-validation`; `EffectiveConfigReporter`
logs the safe effective configuration once per startup via
`ApplicationReadyEvent`, verified never to log a credential value under
any tested scenario, verified never to fail startup even when the
datasource URL is unresolvable.

## Related decisions
ADR 0001 (stdio/stdout reserved for JSON-RPC - the report goes to
stderr), ADR 0004 (credentials via environment variables, never a
committed value - this ADR's redaction logic defends the same boundary
at the logging layer), ADR 0009 (this ADR's own smoke-testing found the
correct H2-pointing mechanism ADR 0009's Tier 1 strategy should actually
use for a real end-to-end packaged-jar run, though Tier 1's existing
`mvn test`-based integration tests were never affected - they construct
their `DataSource` bean directly, not through `application.yml`).
